## Hypotheses

### (a) S2's build — **ruled out as a deterministic cause; a one-off interaction with the warm reboot cannot be excluded**
- For: it was the last change before the reboot, and the install rewrote every unit, wants-symlink, lib, sudoers, udev rule (mtimes 22:44:14–22:44:40).
- Against:
  - The power-cycled boot runs **the same build** (VERSION v0.1.18-draft, `qmanager_update` md5 1ab24a87 = HEAD) and came up normally: all qmanager units active, NRestarts 0.
  - S2's own diff vs c2b39b37 touches no unit, wants-symlink or sudoers line: `install_rm520n.sh` (+env check `QM_DEFER_LIGHTTPD_RESTART` before the lighttpd restart, a comment) and `qmanager_update`. Neither runs at boot.
  - Installer finished cleanly before the reboot (process gone, Step 12/12, no VERSION.pending). No half-done state found: `/etc/data/mobileap_cfg.xml` untouched since 2026-10-28; LAN config intact.
- One reboot under a build that then boots fine is not evidence of a boot-order bug.

### (b) Parallel UI/UX parity sessions / Tailscale — **ruled out**
- Before the reboot, parity sessions only read (P4 at 21:53/22:06). The parity backend rollout was 18 h earlier and survived normal running.
- After the reboot, every parity command failed to connect (table above). Nothing reached the device.
- Tailscale is **not on the modem**: `/usrdata/tailscale` absent, no `tailscaled.service`, no process. P5's two calls (23:02, 23:04) were reads and both failed. The Tailscale in the picture is the GL router (100.108.49.113) and the laptop client (which itself showed "Tailscale is starting… NoState" at 23:12 but still routed to the router).
- iptables now: only the stock QMANAGER_FW and QCMAP rules, MASQUERADE on rmnet_data0; no DNS/DPI state files. Nothing from Custom DNS / Traffic Engine.
- Parity lead asked for any device write I missed (sent 2026-11-02); no device write by them appears in any transcript.

### (c) Vendor stack: QCMAP / 0-byte XML / full `/usrdata` — **disk-full ruled out; QCMAP failing in the failed boot unknown**
- `/usrdata` (= `/etc`, one UBIFS `ubi2_0`) 53% used, 59.9 MB free. All `/etc/data/*.xml` non-zero; the ones QCMAP rewrites each boot (mobileap_firewall, qti_socksv5_conf, mpdn_cfg, dnsmasq.conf) carry 07:49 local = current boot. Not a repeat of I1.
- Whether QCMAP, IPA or the PCIe Ethernet (r8125) came up in the failed boot is unknown — no log survived (journald masked, `/var/log` is tmpfs).
- Background: `pcie.service` (exit 2), `pcie-diag`, `r8168` (exit 1), `ql_ctcc_selfreg` fail on **every** boot, including the healthy one and the Nov 1 boot. Ethernet works anyway through `r8125`. These are not specific to the failed boot.

### (d) Slow / failed boot and the 1970 window — **supported as the most likely class; the exact stage is unknown**
- The failed boot ran ~59 min (22:49:30 → 23:48:42) with: no LAN ping, no SSH, no DHCP lease to the GL router ("Connecting").
- No `reboot_history.json` entry for it. The poller records a boot only once the clock is sane (`alert_engine.sh:457`), and the clock steps only after LTE registration (`ql_time_daemon`). So in that boot **either the poller never ran or the radio never registered**. An Ethernet-only fault would still have registered, stepped the clock and left an entry. So the failure was broader than the LAN link: the boot stalled early, or the modem subsystem plus Ethernet both failed.
- A kernel panic would not explain it on its own: `download_mode=0`, `kernel.panic=5`, `panic_on_oops=1`, so a panic reboots after 5 s instead of sitting in crash-dump mode. A reboot loop or a hang with the watchdog not firing remain possible.
- Earlier warm reboots on this device recovered in about 2–7 min (reboot_history gaps of 125, 152, 399, 463 s), so warm reboots usually work. This one did not; a cold power cycle fixed it.
- Undatable evidence: a batch of 1970-dated early-boot files at `1970-01-01 08:43:5x local` (`/etc/machine-id`, `/usrdata/bind_flag`, `/data/usb/*`, `/etc/.pwd.lock`). It cannot be tied to the outage (see the follow-up, item 4: the RTC model is unreliable).

## Most likely cause
(Updated after S2's step 3: the same tree and the same reboot command came back cleanly on the laptop cable. An intermittent platform fault or a GL-topology interaction remains.)
A vendor/platform-level boot failure on a **warm** reboot, independent of QManager code: the boot after `reboot` at 22:49:25 never brought up Ethernet or LTE registration (or never got that far), and only a cold power cycle cleared it. The same S2 build boots cleanly from cold. No parallel session and no Tailscale component touched the device in the window. Confidence: medium. With no persistent log, the stage where it stopped cannot be proven.

## Follow-up: why would a warm reboot hang when a cold boot of the same tree works?

1. **Reboot command (S2 transcript):** `sync; (sleep 1; reboot) >/dev/null 2>&1 & echo rebooting`, sent 22:49:25, output `rebooting`, exit 0.
   At 22:49:35 `ECONNREFUSED :22`: dropbear had already stopped and the kernel was still answering on bridge0, so shutdown was under way.
   From 22:52 on: handshake timeouts, and by 23:07 no ping. So bridge0/eth0 were down by then.
2. **Stop/timeout settings in S2's tree:** every QManager long-running unit has `TimeoutStopSec=10` (atd `Type=notify`, poller, ping, sites,
   sms-forward, tower-failover, watchcat, console, discord). No `TimeoutStopSec=infinity`, no `KillMode=none` anywhere in `scripts/`.
   The transient `qm-update-worker` (systemd-run, `--collect`) only exists during a UI update. None was running at 22:49 (S2's probes at 22:23–22:36 were 3–9 s `sleep` jobs).
   Device-wide: the only `infinity` stop timeouts are vendor `systemrw-*` / fsck oneshots (RemainAfterExit, no ExecStop). `QCMAP_Bootup` is `Type=notify`, 90 s default.
   **Shutdown safety nets on this device:** `reboot.target` has `JobTimeoutSec=30min` + `JobTimeoutAction=reboot-force`. But `RuntimeWatchdogSec`/`ShutdownWatchdogSec` are unset and there is **no `/dev/watchdog`**.
   A stall inside a stopping unit would therefore self-recover by ~23:19:30. A stall after PID 1 hands off (systemd-shutdown unmount/detach, or the kernel reboot path
   that shuts down the modem subsystem and PCIe) has **no timeout and no watchdog** and would sit until power is cut, which matches what we saw.
   Probe gap: nobody tried the device between 23:24:03 and the power cycle at ~23:48. A 30-min reboot-force followed by a 2–7 min boot could have finished in that gap without anyone seeing it, but then the device should have been up at 23:48, and the user saw it down.
3. **Anything in the tree that runs only on a warm boot:** none found. `/tmp`, `/run`, `/var/volatile` are tmpfs, so they start empty on warm and cold boots alike.
   No persistent "pending" marker was left (no VERSION.pending). The config files the install wrote are the same ones the healthy cold boot read.
   What does differ on a warm boot is hardware and firmware state: PCIe/r8125, IPA, the MPSS modem subsystem and the PMIC RTC are not power-cleared.
4. **Persistent traces from the hung attempt:** none. No file under `/etc`, `/usrdata`, `/data`, `/opt`, `/persist` or the rootfs has an mtime between 22:49:26 and 23:49:11.
   `/var/log` is tmpfs, `wtmp` → `/dev/null`, there is no boot counter, and `reboot_history.json` has only the post-power-cycle boot.
   The 1970-dated file batch cannot date a second boot: the PMIC RTC does not start at 0 (this cold boot's kernel set the clock to `1970-01-01T00:16:57`, yet early files read 08:00:xx local), so the RTC model is unreliable. That earlier dating argument is withdrawn.
   **Result: we cannot tell "hung in shutdown and never reset" from "reset, and the new boot never brought up Ethernet or LTE".**
   Both fit every trace, and neither has anything QManager-specific behind it.

5. **Step 1 and step 2 reboots compared (S2, 2026-11-02):**
   - The reboot binary is the same in both. On this device `/sbin/reboot -> /bin/systemctl`, and `/sbin/init -> ../lib/systemd/systemd`, so `reboot` is `systemctl reboot` (queues `reboot.target` in PID 1), not BusyBox `reboot`. S2's note calling it BusyBox `reboot` is corrected here.
   - Step 1 (hung): `sync; (sleep 1; reboot) &` from an SSH session (dropbear.service cgroup), right after an SSH tarball install of **480cdd32** (`--force --no-reboot`, exited before the reboot).
   - Step 2 (came back as a warm reboot in ~50 s, up 55 s at 08:06:34 local): the updater's own `reboot` from inside the transient `qm-update-worker` unit, right after a UI downgrade to **v0.1.17**. Same 4 vendor unit failures as every boot.
   - What differs: caller cgroup (SSH session vs transient unit), the tree that was installed (480cdd32 vs v0.1.17), and the install path (SSH full install vs CGI updater). The binary and the systemd reboot path are the same.
   - Once PID 1 has queued the job, the caller's cgroup should not matter: step 1 reached the stage where dropbear stopped (22:49:35 refusal). So the caller is a weak candidate. One warm reboot that worked and one that failed is too small a sample to blame the tree; step 3 (SSH install of 480cdd32 + `reboot`, with a pre-reboot capture) tests that directly.
   - Device uptime read 149 s at a later probe (~08:1x local), so another reboot has happened since step 2 (S2's, presumably) and came back.

6. **Step 3 (S2, 08:08:50 local):** same 480cdd32 tree, same SSH-session `sync; (sleep 1; reboot) &` as step 1. It came back with shutdown ≈10 s, up 33 s at 08:09:34.
   Evidence in `/usrdata/s2_prereboot3.txt` (no jobs, no deactivating units, no qm-update-worker) and `/usrdata/s2_shutdown3.txt` (stop jobs queued, 08:08:50–51).
   **This rules out S2's tree and S2's reboot method as a repeatable cause.** One input differs from step 1: the modem now sits on the laptop's Ethernet, not behind the GL-X2000.
   - IP passthrough is off (`IPPassthroughEnable 0`), so the GL is an ordinary DHCP client of the modem's LAN.
   - The GL link alone does not explain everything: the failed boot also left no `reboot_history.json` entry, which needs LTE registration (to set the clock) and a running poller. A LAN-only fault would still have left that entry.
   - So either the boot stalled early or in shutdown (a platform fault, intermittent), or the GL's presence on eth0 at boot interacts with the r8125/PCIe bring-up badly enough to stall more than the LAN. The second has nothing behind it yet.
   - Device uptime 129 s at a later probe, so another reboot has since come back.

Still open: re-test the GL router path (modem → GL WAN → Tailscale) after the power cycle. It was never tested; the modem went straight to the laptop cable.

## Conclusion (2026-11-02, after S2 step 3)

**(a) An unreproduced one-off warm-reboot hang: most likely.** **(b) An Ethernet link or PCIe NIC state problem against the GL-X2000, with the modem otherwise up: unlikely in that form.**

- Against (b): `qmanager-poller` depends only on setup/atd/ping/cfun-fix/sms-storage (device `systemctl show`), not on QCMAP, eth0 or the network.
  If the modem had been up with only the link dead, LTE would have registered, `ql_time_daemon` would have set the clock, and the poller would have added a `reboot_history.json` entry (`alert_engine.sh:457`). **There is no entry** for the 22:49 boot. So LTE registration also failed or the boot never reached the poller, which is more than a NIC link problem.
- `r8168.service` / `pcie.service` fail on **every** boot, including the three healthy reboots today (S2 steps 2 and 3) and the Nov 1 boot. Ethernet runs on `r8125` regardless. Their failure is not specific to the hang.
- (b) survives only in a stronger form: the NIC/PCIe bring-up against the GL peer hangs the kernel or the bus, taking the whole boot down. Nothing points to that yet; it is what the probe below must rule in or out.
- Same tree + same command + same SSH path came back on the laptop cable (step 3). S2's build, its reboot method, the parity sessions and Tailscale are cleared.

## Probe for S5 (settles a vs b)

With the user's OK; it reboots the modem. Modem cabled to the GL-X2000 exactly as before (GL WAN port, DHCP client, IP passthrough off).
1. **Marker A** (before): `date; cat /proc/uptime; ip -br link; ethtool eth0 2>/dev/null` appended to `/usrdata/qmanager/rebootprobe.log` + `sync`, then `reboot` (= `systemctl reboot`).
2. **Marker B** (shutdown, optional rootfs write): a `/lib/systemd/system-shutdown/` hook that appends `B <date>` + `sync` to the same file. If B is missing after a hang, the stall was before systemd-shutdown.
3. **Marker C** (boot): read the same file after recovery; the boot itself is proven by a new `last_boot_id` / `reboot_history.json` entry. For a finer trace, an early oneshot with no network deps that appends `C <boot_id> <uptime>`, then `eth0` carrier/speed, `pgrep QCMAP`, `AT+CEREG?` at +60 s and +300 s.
4. **Peer side during the attempt:** the GL admin page (WAN port link light/speed, WAN state, DHCP log; or `logread`/`ethtool <wan-if>` over the GL's SSH via 100.108.49.113). Link up + no lease = modem booted, LAN service dead. No link = NIC/PCIe or modem not booted. If USB is attached to the laptop, its enumeration (normal composition vs QDLoader 9008 vs nothing) says whether Linux booted.
5. If it hangs, **wait ≥35 min before power-cycling**: `reboot.target` has a 30-min `reboot-force`, so a self-recovery then means the stall was in the unit-stop phase. No recovery means systemd-shutdown or the kernel (no watchdog here).
6. Repeat 3–5 warm reboots on the GL, and the same number on the laptop cable, to get a rate; one hang in N on the GL and none on the laptop would point to (b).

## What would settle it next time
1. **Persistent boot log**: a tiny early unit (or a `qmanager-setup` step) that appends `boot_id`, uptime, `systemctl is-system-running`, failed units, `pgrep QCMAP`, `ip -br link`, `bridge0`/`eth0` state, `AT+CREG?/CEREG?` and `dmesg | tail` to `/usrdata/qmanager/bootlog/<boot_id>.log` at +30 s, +120 s and +600 s (monotonic `OnBootSec`, rotate to 5 boots). The next stuck boot would then show how far it got. (Proposal only, not built.)
2. **Physical check during the outage**: modem LEDs, USB enumeration on a host (QDLoader 9008 = EDL/crash, normal composition = booted), the GL router's port link light, `adb devices` over USB if USB is attached. That separates "never booted" from "booted without network".
3. **Repeat test** (only with the user's OK): several warm `reboot`s on the current build vs the previous build, timing time-to-SSH, to see whether warm reboots fail intermittently on this unit.
4. To tell a shutdown hang from a boot hang: just before `reboot`, write `date; cat /proc/uptime` to `/usrdata/qmanager/last_shutdown_start`, and add a
   `/lib/systemd/system-shutdown/` hook that appends a line plus `sync` just before the kernel reboot. If the hook's line is missing after a hang, the stall was before systemd-shutdown; if it is present and no new boot left a mark, the stall was in the kernel reboot path or the new boot. (Proposal only.)
5. Record a pre-reboot snapshot of `dmesg` and `/proc/uptime` to `/usrdata` before any planned reboot, so the previous boot's tail is kept.
