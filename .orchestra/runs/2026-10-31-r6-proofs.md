## Finding F1 — RG501Q-EU AT channel dead since 03:49:56 UTC (STOP, reported to PM)
Every AT command on the RG501Q fails `modem_not_ready` (`Channel not ready for: …`, 125 lines and counting); `status.json` `system_state: degraded`, `modem_reachable: false`. The QMI lane still answers (`qmi_state up`), but **data is down** (no rmnet IP, no default route, `internet_lost` since 02:31:24 UTC). The first draft said data worked; that was wrong.
Sequence in `/tmp/qmanager.log`: 03:49:33 poller restarts (PID 2171) → 03:49:36 boot-only compound QCAINFO/QNWCFG returns ERROR → 03:49:56 broker: `Command killed by deadline: AT+QMAP="MPDN_RULE";+QMAP="IPPT_NAT"` → from 03:50:03 every command `Channel not ready`. No recovery in 43 min; broker PID 1781 unchanged, NRestarts 0.
Mechanism (static, `native/qmanager_atd/src/at/channel.rs:356-370`): after a timeout the channel is `dirty`; each later command calls `resync()` = AT→OK, else close + reopen + AT→OK once, else `NotReady`. It never succeeds here, so either the modem's AT port is wedged by that QMAP query (firmware) or the reopen path cannot recover. This code is unchanged between 0.7.1 and a643c60b (no `src/at/` change since vendoring except T4.3/R5 lock and flag work), so the OTA to a643c60b does not by itself fix it.
Correction after reading closely: `dirty` stays set after a failed resync, so the broker retried on every command. It did not give up after one reopen. The defect is the cost: each retry held the modem lock up to ~6 s with no backoff, and logged one error line per command.

**F1a (PM yes):** saved to `/usrdata/r6/f1/` on b7e3d6f1: `capture.txt` (broker fd list: fd 5 `/dev/smd11`, fd 3 `/tmp/qmanager_at.lock`; all threads in S state; `fuser` shows only the broker on smd11, smd7 held by `port_bridge smd7 at_usb2`, smd8 by `ql_remotefs_service`; dmesg tail), `qmanager.log`, `qmanager.log.1` (holds the 03:49 events), `qmanager_status.json`, `qmanager_qmi.json`.
**F1c (PM yes):** `systemctl restart qmanager-atd` at 04:50:50 UTC: rc 0, PID 20128, NRestarts 0. Its first command (`AT+QNWCFG="nr5g_time_advance"`) was killed by the 20 s deadline, then `ATI` ×3 and `AT+QMAP="MPDN_RULE"` were all not ready. A fresh process with a fresh open gets no reply, so the port itself is wedged (`f1c.txt`). No reboot, per the PM.
**Root cause:** at 03:49:24–25 UTC, SIGKILL took down QCMAP_ConnectionManagerd, ipacm, adpld, ql-netd, ql-wlanmgr and qtid, all `Restart=no`, so they are now `failed`. In the same second atfwd, csd_server, ql-nw-service, quectel_daemon, qmi_shutdown_modemd, netmgrd, qmuxbridged, mbimd, ql-voice-server and thermal-engine restarted; rmnet_data* came back at 03:49:33, and the poller restarted at 03:49:30. It was not an SSR (subsys0 `crash_count 0`, old broker `qmi_ssr_count 0`), and QManager did not do it (qmanager-watchcat is inactive; qmanager.log is silent 03:47:06–03:49:30). With QCMAP gone, `AT+QMAP` queries pass through atfwd_daemon to a QCMAP that no longer exists and never answer. The first such query (poller boot-only, `qmanager_poller:1240`) wedged the AT port. Data had already been down since 02:31, with LTE flapping from 02:03. Files: `qcmap.txt`, `units_0349.txt`.
**Timeline (reconciled with the PM's 01:03):** data was intermittent from 01:03:52 UTC, with `internet_lost` and `internet_restored` repeating and LTE flapping connected↔unknown. From 02:31:24 it was lost continuously. This is a firmware or carrier event, not QManager. The cause of the 03:49:25 kill is recorded as "vendor stack SIGKILL, origin unknown (UI activity 03:46–03:50; possible vendor recovery after the data loss)". The R5 run log shows only `/tmp` shell runs on the RG501Q, with no action near 03:49. The profile "Smart" apply at 03:50:22 was the poller's own `[boot]` auto-apply after its restart.
**The defect being fixed:** the 0.7.1 broker retried the resync on every command, holding the modem lock up to ~6 s each time with no backoff, which pushed other callers into `Lock acquisition failed`.
