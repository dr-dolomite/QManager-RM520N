## Finding F1 — RG501Q-EU AT channel dead since 03:49:56 UTC (STOP, reported to PM)
Every AT command on the RG501Q fails `modem_not_ready` (`Channel not ready for: …`, 125 lines and counting); `status.json` `system_state: degraded`, `modem_reachable: false`. The QMI lane still answers (`qmi_state up`), but **data is down** (no rmnet IP, no default route, `internet_lost` since 02:31:24 UTC). The first draft said data worked; that was wrong.
Sequence in `/tmp/qmanager.log`: 03:49:33 poller restarts (PID 2171) → 03:49:36 boot-only compound QCAINFO/QNWCFG returns ERROR → 03:49:56 broker: `Command killed by deadline: AT+QMAP="MPDN_RULE";+QMAP="IPPT_NAT"` → from 03:50:03 every command `Channel not ready`. No recovery in 43 min; broker PID 1781 unchanged, NRestarts 0.
Mechanism (static, `native/qmanager_atd/src/at/channel.rs:356-370`): after a timeout the channel is `dirty`; each later command calls `resync()` = AT→OK, else close + reopen + AT→OK once, else `NotReady`. It never succeeds here, so either the modem's AT port is wedged by that QMAP query (firmware) or the reopen path cannot recover. This code is unchanged between 0.7.1 and a643c60b (no `src/at/` change since vendoring except T4.3/R5 lock and flag work), so the OTA to a643c60b does not by itself fix it.
Correction after reading closely: `dirty` stays set after a failed resync, so the broker retried on every command. It did not give up after one reopen. The defect is the cost: each retry held the modem lock up to ~6 s with no backoff, and logged one error line per command.

## Triage tickets (read-only, written during the 3e soak)

**T-A (priority) — `[boot]` profile auto-apply fails open when AT reads fail.** Every poller start runs it: `collect_boot_data` → `auto_apply_profile "$boot_iccid" "boot"` (`qmanager_poller:1330-1332`); no once-per-boot marker; the only guard is the worker PID lock (`profile_mgr.sh` `profile_check_lock`, queues a pending re-apply). It did run on the RG501Q respawn: 03:50:22 `Starting profile apply`. Restart bound: `qmanager-poller.service` `Restart=on-failure`, `RestartSec=5s`, `StartLimitBurst=5` / `StartLimitIntervalSec=3600` (lines 6-7, 20-21) → at most ~5 applies/h from a crash loop, and the counter resets on every boot.
- APN step: the skip check reads `AT+CGCONTRDP=<cid>` (`qmanager_profile_apply:750-757`); when that read FAILS, `current_negotiated` is empty, the step does not skip and runs `apn_apply_write` (CGDCONT → `AT+COPS=2` → `AT+COPS=0`, `apn_apply.sh:442-466`). On the RG501Q at 03:50:48 that is what happened (`AT command failed: AT+CGCONTRDP=1` → `apn_apply_started` → CGDCONT failed, so no detach ran only because the port was dead). With a flaky-but-alive port it would detach/attach on a poller restart. Fix shape: a failed CGCONTRDP read = `mark_step_skipped "apn" "could not read negotiated APN"` (fail closed), not "different".
- IMEI step: fails closed on rc≠0 (`:988-992`) but not on a reply with no 15-digit match (`:994-997` → empty ≠ `p_imei` → EGMR + `AT+CFUN=1,1`). CFUN=1,1 restarts the whole device here, and no marker bounds it, so an IMEI that does not stick (or a mis-parsed CGSN) gives a **reboot loop: boot → poller → auto-apply → EGMR → CFUN=1,1 → boot**. Live profiles carry no IMEI (RG501Q `p_1788063188_64e`: `imei ""`), so not live today. Fix shape: empty parse = fail closed; plus a persistent attempt marker (`/usrdata`, e.g. one CFUN=1,1 per IMEI value per 24 h) checked before the reboot.
