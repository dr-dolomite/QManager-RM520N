## 2. Where WMS lives

**Decision: `qsms` (argv[0] of the `qmanager_atd` binary) gets a WMS backend that talks QRTR in
process. SMS never goes through the broker socket. A long-lived `qsms watch`, run by
`qmanager-sms-forward.service`, is the only indication client.**

Why:
- WMS needs no AT lock and no smd11 (T5.0), and www-data can open `AF_QIPCRTR`. A broker hop
  serialises nothing and adds a dependency. Sending stays behind the authenticated CGI either way
  (any www-data process can already send over QRTR, T5.0 input 8). WMS is not among the broker
  registry's public services, so there is nothing to reuse there.
- Works before and after the broker daemon runs: SMS needs the **binary**, not the socket.
- The forwarder is the only consumer of new-message events (UI does not poll; alerts only send; bot
  has no SMS). Putting the client in the broker's QMI lane would tie forwarding to T7.1.

Transport per platform — fixed, not auto-detected (advocate #5: `qmi/transport.rs:100-118` `lookup`
returns `Ok(None)` on timeout *and* on end-of-list, so "absent" and "slow at boot/SSR" look the same,
and an AT fallback there would silently mark the inbox read):
- **RM520N-GL: WMS only.** A missing WMS server is retried with the registry's backoff up to a
  deadline (list/status/delete 10 s, send 60 s per part), then an error. No AT fallback.
- **RG501Q-EU: the vendored AT backend** (`sms/mod.rs`, in process under `/tmp/qmanager_at.lock`)
  until S0 proves list, status, send, delete and an indication there. Same behaviour as today,
  including mark-read and the long lock hold. The platform comes from QManager's platform profile
  (`docs/reference/platform-profile.md`); the builder reads that doc first.
- The `long_running` (`scan_in_progress`) gate in `client/qsms.rs:23-25` moves onto the AT branch
  only; WMS calls do not wait for a cell scan.

`qsms watch` (RM520N-GL only): registers 0x0001 Event Report (TLV 0x10 = 1) through the crate's
`qmi/registry.rs` reconnect path (name-server backoff, registration replayed on every rebuilt
socket, `registry.rs:1-13,270-279`), so a boot or SSR never makes it exit. It prints one line per
indication (`storage index`) and exits only on a fatal error. This keeps the unit away from its
`StartLimitBurst=5` / 3600 s limit (advocate #3; journald is masked, so a start-limit-hit would be
silent).

Cross-task requirements this plan puts on **T3.1** (to be passed to the project manager):
1. Ship the **S1-built** `dependencies/qmanager_atd` (WMS, `watch`, `tag`), not a pre-S1 build; the
   merge gate is md5 of the shipped file = S1 build, and `qsms watch` run from the shipped path.
2. Install the binary and the `qsms` / `qcmd` links on **both** devices. The T2.3 unit's
   `ConditionPathExists=/usr/bin/qmanager_atd` then cannot be the RG501Q skip (it would start the
   broker there, against D13): T3.1 needs a separate key, e.g. a platform check or an enable marker.

## 3. Read / unread

- WMS list + raw read (0x0031 + 0x0022) never change the tag. After T5.1 a page load no longer
  clears the modem's unread flags on the RM520N-GL (RG501Q on AT: unchanged).
- The UI keeps its client-side read state (`hooks/use-sms-read-state.ts`, `localStorage`
  `qmanager.sms.read.v1`). **No UI change in T5.1.** `qsms tag` (0x0023) exists but is not wired.
- Existing read marks survive only where the **merged** output (after the CGI's `jq` grouping) hashes
  the same: djb2 of `storage|sender|timestamp|content` per merged message. Concat references repeat
  (25 groups, 8-bit refs) and `sort_by(.part)` is stable, so list order and reference width can change
  grouping (advocate #7; RM551E found 16-bit reference differences, `at-broker.md:332-335`). Target is
  parity; any message that differs is listed in S1's proof and shows as unread once after the upgrade
  (see question 1).
- Follow-up, not this task: show modem-side unread state in the inbox (design canon).

## 4. Output contract (diff = 0) and send-failure mapping

CGI responses keep their shape; the CGIs keep their `jq` merge, which selects only `index, sender,
content, timestamp, storage, reference, part`, so `qsms list`'s extra fields (`stat`, `encoding`,
`total`) never reach the response.

- `sms.sh` GET: `{success, messages:[{indexes, sender, content, timestamp, storage}], storage:{used,
  total, me:{used,total}, sm:{used,total}}}` from `qsms list all` + `qsms status all` (0x0036: used =
  max − free). Ordering rule unchanged.
- `sms.sh` POST: `send` → `{success:true}` | `{success:false, error:"send_failed", detail}`; `delete`
  → `partial_failure`; `delete_all` → `delete_all_failed`; `modem_busy` only from the AT backend.
- `sms_forwarding.sh`, `monitoring/alerts.sh`: shapes unchanged.
- Every shell caller extracts `.detail` from `qsms`'s JSON envelope before storing or returning it
  (advocate #6: the forwarder's `$(… 2>&1)` capture would otherwise put raw JSON in `last_error`).

Frontend reads (census): inbox banner shows `detail || error` (`use-sms.ts:139,200,246`); compose
toast is fixed copy (`sms-compose-dialog.tsx:77`); forwarding test toast and the failure list show
`detail` raw (`delivery-health-card.tsx:152,439-441`). So `detail` must be plain language
(No Debug-Build Copy). It stays English, as `sms_tool`'s text is today.

| WMS outcome | `error` | `detail` |
|---|---|---|
| result 0x0036 + TLV 0x12 RP cause N | `send_failed` | `The network rejected the message (cause N).` |
| other QMI error | `send_failed` | `The modem refused the message.` (code goes to the log only) |
| no reply within 60 s per part | `send_failed` | `No reply from the modem.` |
| WMS not available after the retry deadline | `send_failed` / `sms_unavailable` (GET) | `SMS service is not ready yet. Try again in a minute.` |
| bad number | `bad_number` | none (`sms.sh` maps it to a sentence) |
| text needs more than 255 parts | `message_too_long` | none (`sms.sh` maps it to a sentence) |
| bad arguments (parser) | `bad_args` | parser text |

Multi-part: a failed part stops the send; detail prefixes `Part 2 of 3: `. Concat reference: one
byte per send from the monotonic clock.

Encoding note (advocate #10): `pdu.rs` sends text in GSM-7 whenever the GSM alphabet covers it
("café" is GSM-7); the compose dialog calls any non-ASCII text UCS-2 (`sms-compose-dialog.tsx:58`)
and so over-counts parts. Over-counting is safe; aligning the dialog is a UI follow-up.
