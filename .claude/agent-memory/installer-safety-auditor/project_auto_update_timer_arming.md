`qmanager-auto-update.timer`/`.service` (scripts/etc/systemd/system/qmanager-auto-update.{timer,service}) is the daily unattended-update trigger. Facts relevant to any "arm this live from the UI toggle" work:

- `qmanager-auto-update.service` has **no `[Install]` section** — it is only ever started by the timer, never boot-enabled directly. `install_rm520n.sh`'s main `.service` enable loop explicitly skips it (`[ "$svc" = "qmanager-auto-update" ] && continue`, ~line 1568).
- The `.timer` unit has `WantedBy=timers.target`. `install_rm520n.sh` already implements config-gated enable/disable for it at install/OTA time (~lines 1600-1622): checks `qm_config_get update auto_update_enabled 0`, then `ln -sf`/`rm -f` against `TIMERS_WANTS_DIR="/lib/systemd/system/timers.target.wants"` — **manual symlink, not `systemctl enable`**, matching the rest of the installer.
- Runtime belt-and-suspenders: `qmanager_auto_update` itself re-checks `update.auto_update_enabled` before doing anything (scripts/usr/bin/qmanager_auto_update:73-82) — an accidentally-armed timer is a safe no-op, not a silent auto-update.
- The dead crontab-writer in `update.sh` (action=save_auto_update, ~lines 344-366, writing `/var/spool/cron/crontabs/root`) is confirmed genuinely dead: no cron daemon runs on RM520N-GL, and www-data can't write root's crontab anyway even if one did.
- **Sudoers gap for live-arming:** the existing symlink rule (`scripts/etc/sudoers.d/qmanager` lines 17-18) only covers `qmanager*.service` glob patterns into `multi-user.target.wants` — it does not cover `.timer` units or `timers.target.wants` at all. `systemctl start/stop qmanager-*` (lines 11-12) IS already broad enough to start/stop the timer for the current boot, but that alone isn't boot-persistent.
- **Required design for a live-arm root helper:** it must write the SAME `/lib/systemd/system/timers.target.wants/qmanager-auto-update.timer` symlink the installer writes — via manual `ln -sf`/`rm -f`, not `systemctl enable --now`/`disable --now`. Using `systemctl enable` for just this one unit while the installer still uses manual `/lib` symlinks creates exactly the split-brain/orphaned-symlink problem documented in [[project_systemctl_enable_split_brain]] — an install/OTA run and a live UI toggle would each think they own enablement, potentially leaving two symlinks (one in `/etc`, one in `/lib`) or an orphaned one after a mismatched disable.
- Since the helper runs as root already, it can internally call both the symlink management AND `systemctl start`/`stop qmanager-auto-update.timer` (for immediate effect this boot) without needing any additional sudoers grant — one bare-path rule for the helper binary itself is sufficient, consistent with the project's existing bare-path-plus-internal-validation sudoers pattern ([[feedback_sudoers_arg_validation_pattern]] equivalent).
- Live-confirmed 2026-07-20: `qmanager-auto-update.timer` does not exist yet on the test device (`/lib/systemd/system/qmanager-auto-update.*` → No such file or directory) — this feature has not been deployed there, so there is no pre-existing orphaned-symlink state to worry about for THIS unit specifically; the risk is about future consistency between the live-arm helper and the installer, not current on-device drift.
- Crontab sudoers line (`/usr/bin/crontab`, sudoers line 27) is also used by scheduled-reboot (`settings.sh` ~line 258-266), low-power (`settings.sh` ~line 368-373), and tower schedule (`tower/schedule.sh` ~line 124-130) — all still live/active. Retiring the auto-update crontab-writer must NOT remove this sudoers line.

**How to apply:** whenever building the auto-update-arm root helper or touching `update.sh`'s save_auto_update action, use this as the concrete spec for what "arm/disarm" must actually do on disk.
