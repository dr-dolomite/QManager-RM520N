name: project_systemctl_enable_split_brain
description: Live-confirmed systemctl enable/is-enabled semantics vs the manual /lib symlink scheme — the central landmine for any future platform.sh systemctl migration
type: project
---

Confirmed live on the test RM520N-GL (systemd 244.5, 2026-07-20) via read-only `--dry-run` probes and `is-enabled`:

1. **`systemctl enable`/`disable` DO work correctly** on this systemd build — `systemctl enable --dry-run qmanager-ttl.service` reports `Created symlink /etc/systemd/system/multi-user.target.wants/qmanager-ttl.service -> /lib/systemd/system/qmanager-ttl.service`. The `platform.sh` comment ("RM520N-GL's minimal systemd ignores `systemctl enable`") and the matching sudoers comment are **factually wrong** — but the manual-symlink mechanism they chose anyway is not wrong, see point 2.
2. **`systemctl is-enabled` does NOT recognize the existing manual `/lib/systemd/system/multi-user.target.wants/` symlinks that `platform.sh`'s `svc_enable()` creates today.** Live test: `qmanager-ttl.service` has a real `/lib/.../multi-user.target.wants/qmanager-ttl.service -> /lib/systemd/system/qmanager-ttl.service` symlink (confirmed via `ls`), yet `systemctl is-enabled qmanager-ttl.service` reports **`disabled`**. `systemctl enable` only ever targets `/etc/systemd/system/.../wants/`; `systemctl disable` only removes the `/etc` copy (dry-run confirmed: `Removed /etc/systemd/system/multi-user.target.wants/qmanager-ttl.service` — it never touched the `/lib` one).
3. **Consequence for any future `platform.sh` → `systemctl enable/disable/is-enabled` migration:** swapping `svc_is_enabled()` to `systemctl is-enabled` would make every currently-enabled qmanager service (enabled via the legacy `/lib` symlink) suddenly report "disabled" — this feeds `ttl.sh:49`'s UI-facing `autostart` field (cosmetically wrong) but also, more seriously, matches `install_rm520n.sh`'s own pre-install capture logic (`gated_was_enabled`, lines ~1552-1557, which independently does `[ -L "$WANTS_DIR/${svc}.service" ]` against `/lib`) — if that installer logic were ever swapped to use `svc_is_enabled`/`systemctl is-enabled` too, an OTA would silently **fail to re-enable** previously-opted-in gated services (`qmanager-watchcat`, `qmanager-tower-failover`, `qmanager-discord` — see `UCI_GATED_SERVICES`, install_rm520n.sh:113) because the check would report "disabled" even though they were on.
4. Swapping only `svc_disable()` to `systemctl disable` (without a one-time migration step that also removes the legacy `/lib` symlink) leaves the `/lib` symlink **orphaned** — the service keeps autostarting despite the user believing (and the UI showing, via is-enabled) that it's off. Confirmed blast radius via call-site grep: `qmanager_watchcat` (connection watchdog), `qmanager_tower_failover`, `qmanager_discord`, `qmanager_low_power_check` all go through `svc_enable`/`svc_disable`.
5. `install_rm520n.sh` uses manual `ln -sf`/`rm -f` into `/lib` paths **exclusively** — `WANTS_DIR="/lib/systemd/system/multi-user.target.wants"`, `SYSTEMD_DIR="/lib/systemd/system"`, `TIMERS_WANTS_DIR="/lib/systemd/system/timers.target.wants"` (install_rm520n.sh:59-61) — it never calls `systemctl enable`. A `platform.sh`-only migration to `systemctl enable` would diverge from the installer immediately.

**Why this matters:** any pitch to "migrate platform.sh to systemctl enable because a prior experiment disproved the doesn't-work comment" is half right (enable does work) and half a trap (is-enabled semantics don't match the existing manual-symlink installs already in the field). A real migration needs an explicit one-time cleanup/re-home step for every existing `/lib` wants-symlink, done at install/OTA time, in lockstep with the installer — never a `platform.sh`-only swap.

**How to apply:** cite this whenever `platform.sh` service-persistence functions, `install_rm520n.sh`'s `UCI_GATED_SERVICES` gating, or a `systemctl enable` migration proposal comes up. Re-verify against the live device if system behavior might have changed (this was tested 2026-07-20 on systemd 244.5).
