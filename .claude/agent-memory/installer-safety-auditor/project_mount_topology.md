Confirmed live via `mount`/`cat /proc/mounts` on the test RM520N-GL (2026-07-18):

- `ubi0:rootfs` is mounted at `/` only. This is rootfs — contains `/usr`, `/usr/bin`, `/usr/lib`, `/bin`, `/sbin`, `/lib` (including `/lib/systemd/system`). CLAUDE.md's "read-only on stock boot" claim applies to THIS mount only.
- `/dev/ubi2_0` is mounted **independently, multiple times, at**: `/usrdata`, `/etc`, `/data`, `/cache`, `/systemrw`, `/persist`, `/opt`. All confirmed `rw` on live probe, with no evidence anywhere in the codebase of these ever being remounted `ro`. `/opt` specifically is the `opt.mount` systemd bind-mount of `/usrdata/opt` described in `install_rm520n.sh` (`After=network.target`, started via `start-opt-mount.service`, `WantedBy=multi-user.target`) — i.e. **not available during early boot**, only after multi-user.target services start.
- **`/etc` is NOT part of rootfs.** It is its own ubi2_0 mount, always rw. Writes under `/etc` (e.g. `/etc/localtime`, `/etc/qmanager/`, `/etc/data/`) do NOT need any `mount -o remount,rw /` — that remount only matters for true rootfs paths (`/usr/*`, `/lib/systemd/system/*`, `/bin/*`). A comment in `install_rm520n.sh` (`install_udev_rules`, ~line 1319: "Remount rootfs rw — /etc and /usr/lib live on the read-only root") is **stale/inaccurate** for `/etc` given this live evidence — worth correcting if docs-writer touches that area.
- `install_rm520n.sh`'s `main()` never remounts `/` back to `ro`. Only specific runtime-invoked root helpers (`qmanager_console_mgr`, `qmanager_tailscale_mgr`) do their own `mount -o remount,rw /` → work → `sync` → `mount -o remount,ro /` dance around their own privileged writes to rootfs paths. Confirmed live: this test device's rootfs is currently mounted `rw` (likely left that way since the last install/OTA) — but a **fresh boot from stock firmware still starts `ro`** per CLAUDE.md, and nothing guarantees rw survives an arbitrary future reboot. Any new root helper that writes to a **rootfs** path (not `/etc`, not `/opt`, not `/usrdata`) must do its own remount-rw/sync/remount-ro, following the `qmanager_tailscale_mgr` `remount_rw()`/`remount_ro()` idiom — never assume rootfs is rw at invocation time.
- `/usr/share/zoneinfo` does not exist at all on this device (not just empty). `/opt/share/zoneinfo` is Entware's real zoneinfo tree, confirmed populated with valid `TZif`-magic files.
- ubi2_0 has ~97MB free (123.7M total, 22% used) — plenty of headroom for additional Entware packages.
- Re-confirmed 2026-07-19 via a second live `/proc/mounts` probe: `/tmp` is `tmpfs rw,nosuid,nodev` (89.1M, 88.8M free) — genuinely volatile, wiped on every reboot including a daemon-triggered `reboot`. `/etc` is still `/dev/ubi2_0 ubifs rw` (confirmed again, not tmpfs) and `/etc/qmanager/qmanager.conf` was observed with a May 9 mtime still present and readable, i.e. real cross-reboot persistence, not just "should persist per mount table." Any daemon/CGI state that must survive a Tier-4-class reboot must live under `/etc/qmanager/` or `/usrdata/`, never `/tmp/` — see [[project_watchcat_daemon]] for a concrete bug this caught (SIM-failover state file on tmpfs).

**How to apply:** When auditing any new root-helper write path, first classify the destination: rootfs path → requires remount-rw/sync/remount-ro dance; `/etc`, `/etc/qmanager`, `/etc/data`, `/opt`, `/usrdata` path → already persistent+rw, no remount needed at all. Don't assume a task's own framing of "which volume X lives on" is correct — verify against `mount`/`/proc/mounts` directly, this has been wrong in both directions (task prompts and code comments) in prior audits.
