`scripts/usr/bin/qmanager_watchcat` is a state-machine daemon (MONITOR → SUSPECT → RECOVERY → COOLDOWN, plus LOCKED) with 4 escalation tiers: T1 `AT+COPS=2/0` reregister, T2 `AT+CFUN=0/1` radio toggle, T3 `AT+QUIMSLOT` SIM failover, T4 full `reboot` (token-bucketed via `/etc/qmanager/crash.log`, max N/hour, auto-disables past the limit). Installed as `scripts/etc/systemd/system/qmanager-watchcat.service` (`Type=simple`, `ExecStartPre` gates on `qm_config_get watchcat enabled` so a disabled config prevents boot start even if the wants/ symlink exists), listed in `install_rm520n.sh`'s `UCI_GATED_SERVICES` (line 108) so install/OTA only re-enables it if it was already enabled pre-upgrade — confirmed working correctly against the live device (service currently `disabled; inactive`, matching `qm_config_get watchcat enabled` = 0 in `/etc/qmanager/qmanager.conf`).

**Confirmed bug (live-verified 2026-07-19): `SIM_FAILOVER_FILE="/tmp/qmanager_sim_failover"` sits on tmpfs.** Live `/proc/mounts` shows `tmpfs /tmp tmpfs rw,nosuid,nodev` (89 MB, volatile) — this file does NOT survive a Tier-4 reboot. The daemon's own `main()` (qmanager_watchcat ~line 668) tries to resume "stale SIM failover state from before reboot" by reading this file, but if a Tier-4 reboot fires while a Tier-3 failover is active (fully plausible: T3 succeeds, cooldown resets to `monitor`, connectivity fails again later, T3 pre-check skips because current slot == backup slot, escalates straight to T4), the file is wiped and post-reboot the daemon has no memory of `original_sim_slot` — the UI's "revert SIM" feature loses its target slot and the `sim_failover_active` status silently reports `false` even though the modem may still physically be on the backup SIM. This is a genuine silent-state-loss bug, not a hypothetical — must be fixed (e.g. move to `/etc/qmanager/sim_failover.json`, confirmed persistent ubi2_0) before any Tier-4 reboot work on this daemon ships. `DISABLED_FLAG` (`/tmp/qmanager_watchcat_disabled`) has the same class of issue but lower severity — the functional disablement persists correctly via `qm_config_set watchcat enabled 0`, only the UI's "why was this auto-disabled" explanation is lost on reboot.

Other file paths are all fine to be tmpfs-ephemeral: `STATE_FILE`, `PID_FILE`, `RECOVERY_FLAG`, `LOCK_FILE`, `RELOAD_FLAG`, `REVERT_FLAG`, `LONG_RUNNING_FLAG`, `PROFILE_APPLY_PID` are all regenerated/re-derived on daemon start and don't need to cross a reboot.

Reboot safety confirmed sound: the daemon (not any CGI) owns `execute_tier4()`'s `reboot` call, backgrounded as `( sleep 1 && reboot ) &` after `write_state`/log flush, then `exit 0` — no CGI request path calls `reboot` inline. The watchdog CGI (`scripts/www/cgi-bin/quecmanager/monitoring/watchdog.sh`) only ever calls `svc_enable`/`svc_restart`/`svc_stop`/`svc_disable` (backgrounded restart at line 190 via `( svc_restart qmanager_watchcat & )`), never touches `reboot` itself.

Minor non-blocking nit: `qmanager-watchcat.service`'s `After=`/`Wants=` targets `qmanager-poller.service`, but the actual producer of `/tmp/qmanager_ping.json` (`PING_CACHE`, which the daemon reads) is the Rust ping daemon `qmanager-ping.service` (`ExecStart=/usr/bin/qmanager_ping`). Ordering isn't strictly guaranteed against the real data dependency, though the daemon degrades gracefully on stale/missing ping data (`read_ping` returns 1, skips the cycle) so this hasn't caused an incident — worth tightening if the unit is touched anyway.

**How to apply:** any Phase 1 gate on future watchcat/SIM-failover work should re-check whether `SIM_FAILOVER_FILE` has been relocated off tmpfs yet — if not, it's still an open, must-fix item. Phase 5 verification of a watchcat change should specifically test a Tier-4 reboot with an active SIM failover and confirm `sim_failover_active` / `original_sim_slot` survive.
