description: /usrdata/qmanager (QMANAGER_ROOT itself, not a subdir) is 0755 root:root live and in installer — www-data cannot create/rename files directly inside it, so any CGI that mktemp+mv's a file straight into that root (not a www-data-owned subdir) silently no-ops
type: project

Live-confirmed 2026-08-03 on the apn-attach-cycle re-audit (Phase 5, worktree `wt+apn-attach-cycle`): `ls -la /usrdata/qmanager` shows `drwxr-xr-x root root` for the directory itself. `install_rm520n.sh:1095` (`install -d -o root -g root -m 0755 "$QMANAGER_ROOT"`) matches this — deliberate hardening per that line's own comment (self-heals a historical 0777 drift). This is DIFFERENT from `/etc/qmanager` (CONF_DIR), which is `chown -R www-data:www-data` on every install ([[project_conf_dir_recursive_chown]]) — do not conflate the two paths' trust models.

Consequence: `apn.sh`'s `write_setting_json()` (www-data, mktemp+mv pattern into `/usrdata/qmanager/apn_setting.json`) requires write on the parent directory to create the `.tmp.$$` file and rename over the target — www-data has neither, since only owner (root) has write bit on a 0755 dir. Live-confirmed: `apn_setting.json` does not exist on the test device at all (`ls`: No such file or directory), while a sibling `apn_names.json` DOES exist owned by `www-data:dialout` — that file predates the current 0755 hardening (its content can still be read/overwritten in place by its own owner without needing directory write, since existing-file writes only need file-level, not directory-level, permission — but a NEW file, or the mktemp+mv idiom specifically, cannot land).

**Why:** this means `apn.sh`'s own WS6-sidecar write has been silently failing (warn-only, non-fatal by design) independent of any recent change — a pre-existing installer/CGI mismatch, not something a given diff introduces.

**How to apply:** when auditing any change that adds a two-writer (root + www-data) file directly under `/usrdata/qmanager` (not a www-data-owned subdir like `/usrdata/qmanager/locales-staging` which IS `0700 www-data:www-data`), check which UID can actually reach the parent directory before worrying about clobber/ordering between the writers — if www-data can't write there at all, there is no cross-UID clobber risk, only a one-sided silent-failure risk for the www-data path. Confirmed low-risk for `qmanager_profile_apply`'s `_apn_sidecar_converge` (root writer, succeeds) racing `apn.sh`'s `write_setting_json` (www-data writer, already silently no-ops today) — not a regression, and arguably the first path that will ever populate that file. Full mktemp+mv-safety precedent still applies once both writers share a directory that's actually writable by both — see [[project_two_writer_rename_vs_truncate_semantics]].
