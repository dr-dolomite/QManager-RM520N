# Windows GUI Installer (`installer-gui/`)

> **Applies to:** a Windows **host** tool, not device code. It targets both modem
> families through one shared code path — RM520N-GL is the supported tier,
> RG501Q-EU the community tier (warn-and-proceed), RM551E is refused outright.
> Per-device facts live in [`platform-matrix.md`](./platform-matrix.md).

`installer-gui/` is a self-contained Windows application that installs QManager
onto a Quectel modem over USB (ADB) or the LAN (SSH), with **no GitHub access at
any point**. It exists because GitHub is unreachable from mainland China, which
kills QManager's entire normal install path: exactly two links in that chain
touch GitHub — the `qmanager-installer.sh` bootstrap and the `qmanager.tar.gz`
release artifact — and everything downstream of them is either local to the
device or reaches `bin.entware.net`, which **is** reachable from China. So the
GUI embeds the tarball `build.sh` already produces, carries it to the device
itself, and runs the bundled `install_rm520n.sh` from `/tmp`. The China problem
disappears without hosting anything new.

The audience is not shell-fluent, which is the second reason a GUI is the right
shape: the manual alternative (`adb push` + `adb shell` + reading a 3,700-line
installer's output) is precisely the friction that produces half-installed
devices.

The design and implementation plan were written up as local working notes
(not tracked in the repo). The two build commits (`fcce270`, `9afd010`) carry
the full defect archive; this doc carries only what a future task needs.

## What a fresh clone does *not* contain

Four things the build needs are gitignored (`installer-gui/.gitignore`), because
they are binary redistributables or generated output, not source. A clone that
skips them fails in confusing ways:

| Missing | Effect | Fix |
| ------- | ------ | --- |
| `payload/` | `PayloadError: Missing qmanager.tar.gz` at startup | `bun run package` in the repo root, then `python build_installer.py` (which stages it) |
| `vendor/adb/` | `check_vendor_adb` fails the build; ADB transport is dead at runtime | Copy **all three** of `adb.exe`, `AdbWinApi.dll`, `AdbWinUsbApi.dll` from Google platform-tools. adb fails at runtime without the DLLs |
| `src/qmanager_installer/ui/tokens.css` | The UI renders unstyled — `index.html` links it unconditionally | Regenerated by `build_installer.py` (see [Token extraction](#token-extraction)) |
| `ui/fonts/JetBrainsMono-Regular.woff2` | Machine strings fall back to the system mono face | Bundle it locally; Google Fonts is blocked in China, so the UI can never inherit the app's `next/font` loading |

The repo's root `.gitattributes` (lines 18–26) pins every `installer-gui` source
extension to `text eol=lf`. Without it, `core.autocrlf=true` — which this project
uses — would hand a fresh Windows clone CRLF Python and CRLF locale JSON.

## Layering

Two layers with a hard boundary, and the boundary is the reason the preflight
matrix (the part most likely to be wrong) can be tested without a browser, a
device, or a human:

- **`core/`** — pure Python. No UI imports, no `pywebview`. Every decision the
  installer makes is made here, driven entirely through fakes in the test suite.
- **`ui/`** — static HTML/CSS/JS in one `data-view` state machine, reaching
  `core` only through `bridge.py`.
- **`app.py`** is deliberately the **only** module that imports `webview`, so
  `bridge` and `core` stay importable — and therefore testable — with pywebview
  absent.

> ℹ️ NOTE: **Nothing on the bridge may raise.** An exception crossing pywebview's
> `js_api` boundary becomes a rejected JS promise carrying no message the UI ever
> sees — the user gets a frozen screen with no explanation. Every public `Bridge`
> method therefore catches broadly and returns a structured dict
> (`{"error": {"code": ..., "message": ...}}`) instead.

Install, Upgrade and Repair are the same code path — `install_rm520n.sh` is
idempotent and decides fresh-vs-upgrade on-device from `/etc/qmanager/VERSION`.
The GUI *detects and reports* the mode; it never asks the user to pick one.
`Bridge.start()` swaps `InstallRunner` for `UninstallRunner` only when
`action == "uninstall"`, and `UninstallRunner` is a two-line subclass that reuses
the whole sequence through the `script=` seam.

## The exit-code sentinel contract

**Short version: on this platform a command's failure is visible *only* in its
exit status, and neither transport gives us that status honestly — so every
command is rewritten to print its own exit code, and a missing print is treated
as a failure.**

Two facts stack badly here. First, failure on this platform produces no
parseable stdout — `ERROR` never reaches it (see
[`at-command-transport.md`](./at-command-transport.md)). Second, `adb shell`
returns **adb's own** exit status, not the remote command's; a command that died
on the modem still comes back as adb exiting 0. A naive wrapper would therefore
report a failed install as a success, which is the exact class of bug this
project has been bitten by before.

`core/transport/base.py` closes it. `wrap_command()` rewrites every command so
the shell prints its real status on the last line, and `parse_rc()` reads that
line back:

```python
sep = "" if cmd.rstrip().endswith("&") else ";"
return f"{{ {cmd}{sep} }}; echo {RC_SENTINEL}$?"
```

Three properties of that one line are load-bearing:

- **A missing sentinel is failure, never success.** `parse_rc` returns
  `MISSING_SENTINEL_RC` (255) when the last non-blank line isn't a sentinel, or
  when its value isn't numeric. Silence is not consent.
- **The scan runs from the END of the output.** A log line that happens to quote
  `__QM_RC=` cannot shadow the real one.
- **The separator is conditional.** See below.

### Trap 1 — the trailing `&`

`{ cmd }` with no terminator is a shell syntax error, so the `;` is normally
required. But `& ;` is *also* a syntax error, so a command that already ends in
`&` must **not** get one. `&` legally closes a compound command inside a brace
group — but only if nothing but whitespace sits between the `&` and the closing
`}`.

This is not hypothetical: the reboot step is
`sync; (sleep 1; reboot) >/dev/null 2>&1 &`. Before the conditional separator
existed, the shell rejected that whole line before running *anything* — not even
`sync` — and the resulting `Result` was swallowed, so every default install
reported `rebooted=True` for a device that never rebooted and was never synced.

`test_wrap_command_output_is_syntactically_valid_shell` pins it by running
`sh -n` (parse without executing) over the wrapped output. Verified against dash
and BusyBox ash on the live RM520N-GL.

### Trap 2 — `2>&1` binds to the `echo`, not to your command

A redirect trails the single simple command it follows. Appending `2>&1` to
`wrap_command()`'s output redirects only the sentinel `echo`, silently dropping
every stderr line the real command wrote — the opkg / tar / systemctl / curl
diagnostics that are the entire point of the streamed log. `SshTransport.exec_stream`
therefore wraps the wrapped string in one more brace group:

```python
full_cmd = "{ " + wrap_command(cmd) + "; } 2>&1"
```

`AdbTransport` gets this for free by merging at the pipe level
(`stderr=subprocess.STDOUT`), which also keeps the two streams interleaved in the
order they were produced.

> ⚠️ WARNING: the session log is the sub-project's whole support story — a user
> in China who hits a failure sends **one file** and someone abroad diagnoses it.
> Anything that silently drops output defeats that.

### Why SSH does NOT cross-check the channel exit status

> ⚠️ WARNING: **Do not "restore" a guard comparing `parse_rc`'s sentinel against
> paramiko's `recv_exit_status()`.** It looks like a safety improvement. It made
> SSH unusable.

After wrapping, the **last** command in the string is always `echo`, and `echo`
always succeeds — so the SSH channel's exit status is unconditionally 0 for every
wrapped command, passing or failing. It carries no information post-wrapping.
A guard asserting the two agree therefore fires on *every failing command*.

That is fatal rather than cosmetic, because `run_preflight` reads
`/etc/qmanager/VERSION` — a probe whose whole job is to fail on a fresh device.
SSH crashed on the primary use case. Measured on hardware:

```
$ sh -c 'false; echo __QM_RC=$?'
__QM_RC=1        # ...and the shell's own exit status is 0
```

The guard's tests passed only because the fixtures paired `channel_rc=4` with
sentinel `4` — a combination that cannot occur on the wire. **The sentinel is
authoritative; the channel status is not consulted.** The rationale is inlined as
a comment at `core/transport/ssh.py:80-89` so it survives a future refactor, and
was re-verified live afterwards: `cat /etc/qmanager/DEFINITELY_NOT_A_FILE`
returns `rc=1` and does not raise.

## Preflight

`core/preflight.py` holds every device-state decision the GUI makes, and is pure
with respect to the transport. Checks are `PASS` / `INFO` / `WARN` / `BLOCK`; any
single `BLOCK` sets `PreflightReport.blocked` and the Start button is refused.

| Check | Probe | Blocks when |
| ----- | ----- | ----------- |
| `root` | `id -u` | uid is not `0` — `install_rm520n.sh:406-407` dies on non-root, and nothing else verified it before pushing a 5.5 MB payload |
| `identity` | `/etc/quectel-project-version` + `/proc/cmdline` | never blocks; warns when both are empty |
| `model` | `Tier` from the project name | tier `BLOCKED` (RM551E\*), **or** tier `UNKNOWN` with `identity_read_ok=False` |
| `simpleadmin` | four marker paths | any marker exists |
| `existing` | `cat /etc/qmanager/VERSION` | never — decides `INSTALL` / `UPGRADE` / `REPAIR`, and warns on a downgrade |
| `disk` | `df -k /tmp` | free space `< MIN_FREE_KB` (32768) |
| `entware` | `curl`/`wget` HEAD of the real opkg URL | `UNREACHABLE`, `NO_DOWNLOADER`, or anything unmapped |

Both identity sources are read because two modems can be attached at once and a
wrong-device capture is otherwise silent — the same rule CLAUDE.md applies to
live SSH probes.

### `--force` disables the installer's own model block, not just its prompt

The GUI always passes `--force`, because the installer's only interactive prompt
would otherwise sit waiting on a tty that does not exist. But
`install_rm520n.sh:426` puts the **entire** model `case` (lines 435–484) inside
the `else` arm of `if [ "$DO_FORCE" = "1" ]`. `--force` therefore skips the
`RM551E*)` **`die`** as well as the prompt.

**The GUI's model check is the only remaining guard against installing the
RM520N build onto an RM551E.** That is why it fails **closed**, and why
`DeviceInfo.identity_read_ok` exists as a field distinct from the tier:

- Identity read **failed** (non-zero exit — missing file, permission error, dead
  shell) → tier `UNKNOWN`, `identity_read_ok=False` → **BLOCK**. We cannot rule
  out an RM551E, so we do not proceed.
- Identity read **fine** but matched no known prefix → tier `UNKNOWN`,
  `identity_read_ok=True` → **WARN**. This mirrors the installer's own `*` arm,
  which warns and proceeds.

Pinned by `test_unreadable_identity_file_blocks_the_model_gate` and
`test_identity_file_readable_but_unparseable_still_warns`.

### The Entware check blocks rather than warns

An unreachable `bin.entware.net` **with no `/opt/bin/opkg` already present** is a
`BLOCK`, not a warning. The reason is timing: `install_dependencies()` in
`install_rm520n.sh` hard-**dies** fetching opkg, and that death lands *after*
preflight, several steps into the run — so a doomed install still mutates the
device before failing. Warning and proceeding trades a clean refusal for a
half-installed modem.

- `UNREACHABLE_HAVE_OPKG` stays `INFO`. That is the only case the spec's "Entware
  may already be present" rationale ever covered.
- `NO_DOWNLOADER` blocks — the installer dies outright without curl or wget.
- **Unmapped or empty probe output also fails closed.** A timed-out probe or a
  half-open connection's garbage cannot be distinguished from a reachable mirror,
  and "reachable" is the guess that mutates the device before dying.

The probe hits the actual binary path
(`http://bin.entware.net/armv7sf-k3.2/installer/opkg`), not the site root: a
mirror can serve a landing page at `/` while 404ing the real installer path. The
arch literal matches `install_dependencies()`'s own `ENTWARE_ARCH`.

### Two shell details that silently break the probes

> ⚠️ WARNING: both of these produce *wrong data*, not errors, and neither is
> obvious on reading.

- **The SimpleAdmin probe must end `; true`.** A `for p in …; do [ -e "$p" ] && echo "$p"; done`
  loop exits non-zero when the **last** marker is absent — which is the normal
  case on a clean device. Without the trailing `; true`, every clean device reads
  as a transport failure. (`test_simpleadmin_probe_ends_with_true_so_a_clean_device_is_not_a_failure`)
- **Disk space uses `df -k`.** BusyBox `df` without `-k` may report 512-byte
  blocks, which silently halves the measured free space and can block a device
  that has plenty. (`test_disk_probe_forces_kilobyte_blocks`)

## The install sequence

`InstallRunner.run()` is five steps: **push → verify → extract → run → reboot.**

1. **push** the tarball to `/tmp/qmanager.tar.gz`.
2. **verify** `sha256sum` on the device against `Payload.sha256`. A truncated
   push is otherwise completely invisible; corrupting one payload byte was
   confirmed to be refused here, before `tar xzf` is ever reached.
3. **extract** to `/tmp/qmanager_install`.
4. **run** `bash …/install_rm520n.sh --force --no-reboot`, streaming output.
   Progress comes from parsing the installer's own `[Step %d/%d]` marker
   (`install_rm520n.sh:271`) out of the stream — there is no separate progress
   channel.
5. **reboot**, as a *separate command*.

### The reboot separation

**`install_rm520n.sh` is ALWAYS invoked `--no-reboot`.** If the installer rebooted
itself, its exit code would never come back — and a genuine mid-install failure
would be indistinguishable from a normal reboot. Both look identical from the
Windows side: the transport goes away.

Splitting the reboot out gives two unambiguous rules:

- A **transport death during the reboot command is the SUCCESS path** — a
  rebooting device is supposed to stop answering, so `TransportError` there sets
  `rebooted=True`.
- A **non-zero `Result` from the reboot command is a REAL failure** and raises.
  This is the case Trap 1 above produced: a shell syntax error meant `sync` never
  ran, yet the run reported a successful reboot.

(`test_installer_is_always_invoked_with_no_reboot`,
`test_transport_dying_during_reboot_is_success_not_failure`,
`test_reboot_command_failing_without_raising_is_not_reported_as_rebooted`)

### The "Skip package installation" option

**Short version: this is the GUI's answer to a device with NO working internet
at all — not the GFW-blocked-GitHub case the whole sub-project otherwise
exists to route around, but a modem whose SIM has no data plan or is out of
coverage.** Without it, a fresh install always calls `install_dependencies()`
on the device, which shells out to `opkg update` / `opkg install <pkg>`
against `bin.entware.net`. On a device with zero WAN, those calls don't fail
fast — they stall on a half-open TCP connection for up to
`DEFAULT_EXEC_STREAM_TIMEOUT` (30 minutes), which reads to the user as a
frozen installer stuck on one step.

The checkbox lives on the preflight screen (`option.skip_packages` /
`option.skip_packages.help` — a question-mark tooltip trigger next to the
"Reboot when finished" switch, `ui/index.html`'s `#skip-packages`), defaults
**unchecked**, and appends `--skip-packages` to the install command —
`InstallOptions.skip_packages` → `InstallRunner.run()` (`core/installer.py`).
It mirrors the flag `qmanager_update` already passes on every OTA re-install,
which gates `install_dependencies()` in `install_rm520n.sh`.

It only helps if Entware/dropbear/etc. are **already on the device** from an
earlier install attempt — `install_rm520n.sh --skip-packages` on a device that
has never had Entware bootstrapped just fails later for a different reason
(no `opkg`, no `dropbear`). The GUI does not detect this for the user; the
checkbox is a manual escape hatch, not an automatic decision.

`InstallRunner.run()` only appends the flag when `self._script ==
"install_rm520n.sh"` — `uninstall_rm520n.sh` has no `--skip-packages` option
and dies on "Unknown option" if it receives one. `UninstallRunner` reuses
`InstallRunner.run()` verbatim (see "Install, Upgrade and Repair are the same
code path" above), so this guard is the only thing stopping a stray
`skip_packages=True` from reaching an uninstall run and breaking it.
(`test_uninstall_never_passes_skip_packages`,
`test_skip_packages_requested_adds_the_flag`,
`test_skip_packages_not_requested_omits_the_flag`.)

### There is deliberately NO cancellation gate after the install exits 0

`run()` checks the cancel event before each of the first four steps, and then
stops checking. Past the `exit_code != 0` test the device is **fully installed**
and only the separate reboot remains. Treating a cancel landing in that ~10 ms
window as `InstallCancelled` would tell the user the device "may be left
partially modified" and send them to re-run an installer that had already
succeeded — a lie in the one direction that actually costs something. A late
cancel therefore just skips the reboot, which is identical to unchecking "Reboot
when finished".

(`test_cancel_after_the_script_succeeded_is_not_reported_as_cancelled`)

## Cancel and the wall-clock deadline

Cancellation has **two halves**, and both are needed:

- `InstallRunner`'s `threading.Event`, checked between steps.
- `Transport.cancel()`, which terminates the adb `Popen` or closes the paramiko
  channel — safe from another thread, and a no-op when nothing is running. This
  is the half that matters, because the stall this feature exists for happens
  *mid-stream* during the ~3-minute install, not at a step boundary.

`DEFAULT_EXEC_STREAM_TIMEOUT = 1800` bounds the **read loop itself**, via a
`threading.Timer` watchdog that aborts the same process/channel `cancel()` would.
A timeout value handed only to a post-hoc `proc.wait()` is not a bound at all —
it is consulted after the loop has already drained to EOF, so a command that
hangs without closing stdout blocks forever. The target scenario is concrete:
`opkg` stalling on a half-open TCP connection to `bin.entware.net` over a
mainland-China ISP link.

**Cancelled is a third terminal state, not "failed" wearing a different
message.** `InstallCancelled` is its own exception and `Bridge.poll()` reports
`state: "cancelled"`, because a cancelled run is neither a success nor a failure
and callers must not be able to mistake one for the other.

> ⚠️ WARNING: cancelling rolls **nothing** back. `install_rm520n.sh` mutates
> `/etc/qmanager`, `/usr/bin` and `/lib/systemd/system` as it goes. The UI says so
> (`run.cancelled.detail`) and tells the user that re-running is the fix.

Verified live: a reader parked in `exec_stream` on a real paramiko channel,
cancelled from another thread, unblocked in 3.0 s against a 45 s sleep.

## Two defects that exist ONLY in the frozen build

**Short version: dev and the shipped `.exe` resolve paths and imports
differently, so a whole class of bug passes every test and fails only for the
user.** Both of these did exactly that; both were found by building the artifact,
not by reading code.

### 1. PyInstaller ≥ 6 buries `--add-binary` under `_internal/`

PyInstaller 6 onedir mode places everything from `--add-binary` / `--add-data`
under `dist/<name>/_internal/`, leaving only the launcher exe beside it. The
runtime adb resolver computes `Path(sys.executable).parent / "vendor" / "adb" / "adb.exe"`
— i.e. **beside the exe** — and would never look there.

So `build_pyinstaller_argv()` deliberately has **no `--add-binary` for adb**, and
`stage_runtime_assets()` copies `vendor/adb/`, `locales/` and `payload/` beside
the exe with `shutil.copytree()` after PyInstaller returns.

`ui/` is the one exception that legitimately uses `--add-data`, because it is read
back through `sys._MEIPASS`, which resolves into `_internal/` correctly. Four
resolvers, three of one kind and one of the other:

| Asset | Frozen resolver | Must land |
| ----- | --------------- | --------- |
| `ui/` (`app.py:ui_dir`) | `sys._MEIPASS / "qmanager_installer" / "ui"` | under `_internal/` |
| `payload/` (`core/payload.py:payload_root`) | `Path(sys.executable).parent` | beside the exe |
| `locales/` (`i18n.py:locales_root`) | `Path(sys.executable).parent` | beside the exe |
| `vendor/adb/` (`bridge.py:adb_path`) | `Path(sys.executable).parent` | beside the exe |

The onedir choice is itself a requirement, not a preference: locale files must
stay plain, editable JSON on disk so a native speaker can correct one and send it
back, and a onefile build buries them in a temp extraction directory.

### 2. `__main__.py` is the entry SCRIPT, so its imports must be ABSOLUTE

`build_installer.py` hands `src/qmanager_installer/__main__.py` to PyInstaller as
the entry script. PyInstaller executes an entry script as `__main__` **with no
parent package**, so `from .app import run` raises

```
ImportError: attempted relative import with no known parent package
```

at launch — in the frozen build only. It resolves fine under
`python -m qmanager_installer`, which is why the entire suite never saw it.

`tests/test_entrypoint.py` guards this: it walks `__main__.py`'s AST and fails on
any `ImportFrom` with `level > 0`, plus a second test asserting
`build_installer.py` still names `__main__.py` as the entry script — so if the
entry point ever moves, the guarantee is forced to move with it.

## Token extraction

`build_installer.py` regenerates `src/qmanager_installer/ui/tokens.css` from
`app/globals.css` on every build, so the installer's look cannot drift from
`DESIGN.md`. The UI is authored purely against those `var()` references — no
literal colour, no raw duration.

**It must extract THREE top-level blocks, not two:** `@theme inline`, the first
`:root`, and the first `.dark`.

The shape and easing scales live in `@theme inline`, which spans
`app/globals.css:84-232` — `--radius-field` at 217, `--radius-card` at 219,
`--ease-standard` at 228 — and **closes before the first `:root` opens at 235**.
Only the duration scale (`--duration-standard`, line 254) is in `:root`. Taking
just `:root` + `.dark` silently ships square cards and a `transition` shorthand
with a missing ease term, which CSS drops entirely — no transitions at all.

Two guards keep this honest:

- `extract_token_blocks()` rewrites the `@theme inline {` header to `:root {`
  (its body is plain custom properties, so the rewrite is safe) and then refuses
  the output if `@variant`, `@apply` or `@theme` survived — globals.css holds
  four **later** `:root` blocks carrying `@variant` at-rules a plain browser
  cannot parse, so "first block only" is load-bearing.
- `assert_required_tokens()` checks an explicit `REQUIRED_TOKENS` allow-list, so
  a token *migrating between blocks* in a future globals.css refactor fails the
  build loudly instead of shipping a UI with a missing radius.

> ℹ️ NOTE: `REQUIRED_TOKENS` was transcribed by hand from the plan's Task 11 CSS
> listing before `ui/styles.css` existed. Now that it exists, prefer scanning it
> for `var(--…)` references over maintaining the list by hand.

## The saved connection

Ticking **Remember password** on the SSH pane writes
`%LOCALAPPDATA%\QManagerInstaller\settings.json`, and the next launch
prefills host, username, the transport tab and the UI language from it. This
is the only thing the sub-project persists; before it, even the locale picker
reset to English on every launch.

### The password never leaves Python

`Bridge.saved_connection()` returns `has_password: true` — a bool, never the
secret. The field shows a *"Using saved password"* placeholder instead of
fake dots, and an empty field at connect time is the signal to use the saved
one: `connect_ssh` decrypts it in Python and hands it straight to paramiko.
So a root password never enters the WebView's DOM, never sits in the JS heap,
and cannot surface in a WebView2 crash dump.

The one thing this costs: **a genuinely empty SSH password is unexpressible
once a blob is saved.** Not a real case for `root` on these modems, but it is
the reason the rule is "empty means saved" rather than a separate flag.

### DPAPI, and why the blob is safe to ship around

`core/dpapi.py` calls `CryptProtectData` / `CryptUnprotectData` through
`ctypes` — no new dependency, nothing for PyInstaller to miss, and the key
never leaves the OS. DPAPI ("Data Protection API") encrypts a secret to the
**logged-in Windows account on this machine**, so the blob is inert
everywhere else. That is the entire security argument for saving a root
password at all: `settings.json` can be copied to a USB stick, emailed, or
committed by accident and it still leaks nothing.

Both calls pass a fixed app entropy (`QManagerInstaller/ssh/v1`), a second
secret DPAPI requires again at decrypt time. Without it, any process running
as the same user could open the blob just by handing the file to
`CryptUnprotectData`.

> ℹ️ NOTE: this is also why the file lives under `%LOCALAPPDATA%` rather than
> beside the exe, where the locales and session logs sit. The session log is
> the sub-project's whole support story — the user zips that folder and sends
> it — and a support bundle that also carries a root password is a hazard.
> The portability a same-folder file would seem to buy is illusory: a DPAPI
> blob does not survive the trip to another PC anyway.

### Every failure degrades to "not remembered"

Nothing in `prefs.py` or `dpapi.py` raises. `unprotect` returns `None` — not
an exception — for a blob from another Windows account, garbage base64, a
truncated file, or a non-Windows host; `load_prefs` returns the shipped
defaults for a corrupt file; `save_prefs` returns `False` on a read-only or
roaming profile; unknown keys from a future version are dropped rather than
passed to the constructor. Each of those reads back as exactly what a fresh
install looks like.

That is not defensive habit, it is the bridge contract: an exception crossing
pywebview's `js_api` boundary becomes a rejected JS promise carrying no
message the UI ever sees, so the user gets a frozen connect screen with no
explanation. Silence-with-defaults is the only safe failure mode here.

### Two rules that are easy to "simplify" away

- **Credentials are persisted only after they have worked.** A failed
  `connect_ssh` writes nothing at all — not even the host. A remembered wrong
  password would be retried on every launch against an account that may lock
  out.
- **Un-ticking the box calls `forget()` immediately**, not at the next
  connect. A control that says "forget this" and then keeps it until later is
  a lie. It drops the secret and keeps the address.

### Testing it

`tests/test_dpapi.py` is the only file that calls real `crypt32`, and skips
off Windows; everything else drives an injected `FakeCipher` through the
`cipher=` seam, and `prefs_root=` keeps the suite out of the developer's own
`%LOCALAPPDATA%`. Both seams exist on `Bridge.__init__` for that reason.

> ⚠️ WARNING: a fake cipher that leaves the plaintext readable silently
> defeats the whole harness. The first `FakeCipher` returned
> `"enc:" + plaintext`, and
> `test_the_plaintext_password_never_reaches_the_disk` caught it on the first
> run — the assertion was right, the fake was wrong, and the fake was
> hardened rather than the assertion weakened. Keep any replacement actually
> obscuring.

## Payload staleness — what `stage_payload` does and does not catch

Nothing in this sub-project re-rolls the tarball: the artifact `build.sh`
produced is the one that ships, byte for byte. `stage_payload()` copies
`qmanager-build/{qmanager.tar.gz,sha256sum.txt}` into `payload/` and stamps a
`VERSION` file.

It does not trust `package.json` blindly. It reads the `VERSION=` line out of the
tarball's own `qmanager_install/install_rm520n.sh` — the value the device will
actually report after install — and **fails the build** when the two disagree.

> ⚠️ WARNING: **this catches VERSION drift, not CONTENT drift.** A tarball can be
> stale at an unchanged version and pass this check cleanly. That is not
> theoretical: this repo's `qmanager-build/` artifact was content-stale (18
> `scripts/test` entries dropped by `048c2d3`) while its `VERSION=` still matched.
> The only fix is to rebuild — run `bun run package` before packaging the
> installer, always, not only when the version number moved.

## Testing

`core/` is driven entirely through fakes: **143 tests, no device required**.
`bridge.py` and `core/` do not import `webview`, so the suite runs without
pywebview installed.

```
cd installer-gui
.venv\Scripts\pytest
```

> ⚠️ WARNING: **a fake will happily accept an implementation that cannot work
> against real hardware.** This sub-project shipped that mistake twice before it
> was caught — the SSH fixtures paired a channel status and a sentinel in a
> combination that cannot occur on the wire, and the reboot command that was a
> shell syntax error had a passing test asserting it "ran". A green suite here is
> necessary and not sufficient; anything touching the wire format, the transport
> lifecycle, or the frozen artifact needs a real measurement.

Three test files exist specifically because a fake could not have caught the bug:

- `tests/test_transport_base.py::test_wrap_command_output_is_syntactically_valid_shell`
  — shells out to `sh -n`.
- `tests/test_entrypoint.py` — parses the entry script's AST, because the failure
  only exists once frozen.
- `tests/test_build_tokens.py` — asserts against the real `app/globals.css`.

**Still unverified, deliberately** (as of `9afd010`): no visual screenshot of the
rendered UI, no ADB end-to-end run (no USB device was attached), and no real
install — the user gated that.
